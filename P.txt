## 1. 利用者から共有された事実

CloudFormation管理のElastiCache ReplicationGroupを、過去にWebコンソールから6.2.6→7.1へ更新済みです。

| 項目 | CloudFormation管理定義 | 現在の実環境 |
| --- | --- | --- |
| EngineVersion | 6.2.6 | 7.1.0 |
| ParameterGroupのFamily | redis6.x | redis7 |
| 実機の適用グループ名 | 管理定義の参照先は要照合 | default.redis7.cluster.on |

FamilyはParameterGroup側の設定です。ReplicationGroup側ではCacheParameterGroupNameで適用するグループ名を指定します。
この表のFamily差は、管理定義が参照する旧6系グループと、実機が適用するdefault.redis7.cluster.onとの比較です。旧6-2が管理するグループ自体のFamilyがredis7へ変化した、と確認したものではありません。

構成・状態：

- 6：ルートテンプレート。
- 6-1：ReplicationGroupの子テンプレート。
- 6-2：既存ParameterGroupの子テンプレート。
- 新規V2：変更セットにAddが出たParameterGroup用ネストリソース。論理IDは、共有表記でEcr001ElastiCachRedisParameterGroupStackV2。
- ルート実スタック名：TestFclElastiCacheStack。
- 失敗したRedis子スタック名：TestFclElastiCacheStack-Ecr001ElastiCacheRedisStack-4F1IQA6Z76RB。
- ロールバックのエラーが出たリソース論理ID：AwsElastiCacheReplicationGroup。
- ルートの現在状態：UPDATE_ROLLBACK_FAILED。
- V2子スタックの現在状態と、該当RGリソース行の現在ステータスは未確認。

以前共有された6-1は、CacheParameterGroupNameをImportValueで参照し、6-2がグループ名をExportする構成でした。ただし、今回V2を追加した適用版テンプレートとの一致は未確認です。

変更セットで共有された表示：

- V2ネストリソース：Add。
- 既存RedisのEngineVersion：6.2→7.1、RequiresRecreation=Never。
- 別途、before側7.1／after側7.1という表示も共有されています。同じ変更セット・子スタック・論理ID・時点の情報か、元画面の項目名を含め未確認です。

## 2. 発生したエラー

利用者の説明では、更新時にエラー1、その後のロールバックでエラー2が発生しました。イベントの時刻とステータスによる最終照合は未実施です。

エラー1：

```text
Incompatible cache parameter group.
The cache has Parameter Group Family redis7.
The requested cache parameter group has Parameter Group Family redis6.x.
```

エラー2（ロールバック時、AwsElastiCacheReplicationGroup）：

```text
Cannot modify redis from 7.1.0 to redis version 6.2.6
```

## 3. 現時点の原因整理

**背景として確認された不整合**

管理定義は6.2.6／redis6.xのまま、実環境は7.1.0／redis7です。以下の直接原因は、共有された管理値とエラー内容に整合します。

| 処理 | 直接原因 | 公式根拠 |
| --- | --- | --- |
| 更新 | redis7環境へのredis6.xグループの指定が、互換性不一致で拒否された | R1・R3 |
| ロールバック | 更新前の構成へ戻す過程で、7.1.0→6.2.6の変更要求がダウングレード制約により拒否された | R2・R3 |

**未確定の参照経路**

最初に照合したい仮説は、V2を追加しても、既存6-1のImportValueが旧Exportを参照し、旧redis6.xグループ名が選ばれたという経路です。

ただし、旧グループ名と、その値が親入力・ImportValue・Mapping・Condition・S3上の旧版等のどこから来たかは未確定です。V2のAddだけでは、V2の実Familyや、既存RedisがV2を使うことを証明できません。

## 4. 変更セット・ドリフトの解釈

- RequiresRecreation=Neverは「このプロパティ変更で再作成が不要」という意味です。更新成功や互換性の保証ではありません。【R4】
- 変更セットは更新成功を保証しません。【R5】
- ネストされたスタックのプロパティ単位変更セットでは、クロススタック参照を解決しないという公式の制限があります。【R6】
- 2026-11-18取得の東京公式スキーマでは、ReplicationGroupのEngineVersionとCacheParameterGroupNameはwriteOnlyPropertiesです。この2項目について、ドリフト検出のIN_SYNCだけで実機との一致を証明できる前提にはしません。【R9・R10】
- ReplicationGroupとParameterGroup自体は、ドリフト検出対応です。ElastiCache全体が未対応という意味ではありません。【R11】
- drift-aware変更セットでも、write-only項目は前回デプロイ値との比較になります。before／afterの値だけで整合済みやロールバック先7.1を判断せず、BeforeValueFrom等も確認します。【R12】

write-onlyという事実だけから、CloudFormationが今回どのAPI引数を送信したかまでは断定できません。
今回確認した公式資料の範囲では、Redis6→7専用のCloudFormation既知不具合という説明は確認できていません。一般仕様に基づく説明と、個別不具合の認定を区別してください。

## 5. 原因確定のために照合する資料

最優先はCloudTrailの実送信値です。ElastiCacheのAPI呼び出し・要求内容はCloudTrailに記録されます。【R13】

1. 更新時とロールバック時のModifyReplicationGroup、必要ならModifyCacheCluster。
2. 各イベントのeventTime、対象ID、errorMessage、requestID、requestParameters.engineVersion、requestParameters.cacheParameterGroupName。
3. V2のCreateCacheParameterGroupで指定されたFamilyと、実際のグループ名。
4. その時点の6-1のCacheParameterGroupNameと、ImportValue先のExport名・値。
5. 親から子へ渡した入力値、V2のOutputs、TemplateURLとS3オブジェクトの内容・版。
6. 更新前の成功時、今回の提出版、現在の保存済み版を区別したテンプレート・入力値。

エラー1が実際にはロールバック中だった場合は、それより前の最初の更新失敗原因を探し直してください。

## 6. 復旧案：未実行・条件確認が必要

通常更新の前に、親からロールバックの続行でUPDATE_ROLLBACK_COMPLETEへ戻すのが基本です。ContinueUpdateRollbackに修正テンプレートを渡す引数はありません。【R7・R8】

今回の候補は、7.1を維持し、ダウングレード拒否でロールバックに失敗したRGの処理だけを必要最小限スキップすることです。

操作先の親：

```text
TestFclElastiCacheStack
```

スキップ指定候補（API／CLIの指定形式。実行コマンドではありません）：

```text
TestFclElastiCacheStack-Ecr001ElastiCacheRedisStack-4F1IQA6Z76RB.AwsElastiCacheReplicationGroup
```

実行前の確認条件：

- 該当RGのリソース行が、ロールバック自体の失敗を理由とするUPDATE_FAILEDであること。過去のエラーに論理IDが出たことだけで確定しない。【R8】
- 実機7.1・default.redis7.cluster.onの適用状態と稼働状態を確認する。
- V2子スタックの状態、V2の物理名、他キャッシュでの使用、Export参照を確認する。対象RGはV2を使っていませんが、V2全体の削除可否は未確定です。
- 新規V2はロールバックで削除され得ます。使用中のPGは削除できないため、他の使用先や別の失敗があれば追加判断が必要です。【R14】
- 子スタック自体を丸ごとスキップする場合は別の状態条件があります。子スタックがUPDATE_ROLLBACK_FAILEDであっても、その理由だけで子全体をスキップする指定にはしません。【R8】

スキップ後も実機と管理定義の不整合は残ります。復旧後の整合化用の変更内容を用意し、EngineVersionとCacheParameterGroupName、その参照経路を実機に合わせます。【R7・R8】
既存PGのFamilyを変更する場合は置換になります。また、Importが残るExport値は変更できません。復旧後の設計でも、この2つの条件を確認してください。【R15・R16】
以前の3段階手順は更新可能な安定状態が前提です。今回のV2追加構成・UPDATE_ROLLBACK_FAILED状態へ、そのまま適用しないでください。
