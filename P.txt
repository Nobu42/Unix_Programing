2. 指定形式の判定

正式なパラメータ名はResourcesToSkip。
公式のネスト内リソース指定形式は、NestedStackName.ResourceLogicalID。【S1】

今回の候補は次のとおり。下の行全体が1つの値であり、途中に改行・空白を入れない。

TestFclElastiCacheStack-Ecr001ElastiCacheRedisStack-4F1IQA6Z76RB.AwsElastiCacheReplicationGroup

画面上で自動的に折り返されることは問題ない。実際の入力に改行を含めない。
子スタックの実名と、親テンプレートにある子スタックの論理IDは区別する。

操作先のStackNameは親のTestFclElastiCacheStack。
上記の候補は公式の指定形式・許容文字パターンに一致する。ただし、文字列が正しいことと、現在スキップ可能な状態であることは別。【S1】

3. スキップ対象としての必須条件

・AwsElastiCacheReplicationGroupの現在のリソース行がUPDATE_FAILEDであること。
・その理由が、ロールバック自体の失敗であること。今回は6.2.6への復帰拒否と照合する。
・親がUPDATE_ROLLBACK_FAILEDであることや、過去のエラーに論理IDが出たことだけでは、この条件を満たした証拠にならない。
・対象は必要最小限とする。今回はRG1件を候補としているが、他の失敗の有無は別途確認する。【S1】

4. 子スタックのDELETE状態条件との違い

公式のDELETE_IN_PROGRESS／DELETE_COMPLETE／DELETE_FAILEDという条件は、AWS::CloudFormation::Stackリソース自体をスキップする場合の条件。

今回の指定は、子スタック内のAWS::ElastiCache::ReplicationGroupをスキップするもの。
したがって、今回のRG指定のために、子スタック自身がDELETE系状態である必要はない。
一方、子スタックがUPDATE_ROLLBACK_FAILEDであっても、それだけを理由に子全体をスキップしてよいとは判断しない。【S1】

5. スキップ後の状態

以下は、スキップ指定が受理され、残るロールバック処理も成功した場合の想定。

対象RGのリソース行：
・CloudFormationがUPDATE_COMPLETEに設定する。【S1】【S2】
・これはスキップ扱いで状態を進めることを意味し、実機と管理定義の整合完了ではない。

既存Redis子スタック自身：
・親からの続行により、子もロールバックの対象になる。
・残るロールバックが成功した場合、UPDATE_ROLLBACK_COMPLETEを想定する。
・この子スタック自身の状態と、親に表示されるAWS::CloudFormation::Stackのリソース行を混同しない。【S2】【S3】

親スタック：
・全体の続行が成功すればUPDATE_ROLLBACK_COMPLETEになる。【S1】【S2】
・UPDATE_COMPLETEになることを、今回の親のロールバック完了条件にはしない。

親で想定する流れ：

UPDATE_ROLLBACK_FAILED
→ UPDATE_ROLLBACK_IN_PROGRESS
→ 必要に応じてUPDATE_ROLLBACK_COMPLETE_CLEANUP_IN_PROGRESS
→ UPDATE_ROLLBACK_COMPLETE

中間状態の表示は処理内容による。cleanupは、失敗した更新で新規作成したリソース等の後片付けを示す。【S3】

6. 今回、保証できないこと・復旧後に必要なこと

・RGを1件スキップしただけで、親・子すべての復旧成功が保証されるわけではない。
・V2の削除等、残るロールバック処理が別途失敗すれば、再び停止する可能性がある。
・対象RGはdefault.redis7.cluster.onを使用しているが、V2の他キャッシュでの使用・Export参照・現在状態は別に確認する。
・今回の方針は、対象RGを6系へ戻す処理を省略し、7.1を維持して復旧すること。実機のバージョン・適用グループ・稼働状態は実行後にも確認する。
・スキップ後も管理定義との不整合は残る。無関係な通常更新を先に行わず、復旧後の整合化用の変更内容を用意する。【S1】【S2】

現場AIには、まず現在のRGリソース行とV2子の状態を照合し、候補の成立条件・残る停止要因・復旧後の確認項目を返してほしい。未確認情報を推測で補完しない。

【S1】ContinueUpdateRollback API
