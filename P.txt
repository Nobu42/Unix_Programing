# Redis更新失敗：CloudTrailの確認手順と調査対象イベント

確認日：2026-11-18
用途：現場AIチャットへの引継ぎ。AWS公式仕様、確認手順、今回の未確認事項を区別する。

現場のAWS環境には接続していません。以下はログの読み取り手順であり、更新・ロールバック続行・設定変更は行っていません。実際のCloudTrailイベントは未取得です。

## 1. 最初に確認するイベント

既存のElastiCache ReplicationGroupに対する変更要求は、まず次を探します。【R1・R2・R4】

```text
eventSource = elasticache.amazonaws.com
eventName   = ModifyReplicationGroup

確認するJSONパス（そのイベントに記録されている場合）
requestParameters.replicationGroupId
requestParameters.engineVersion
requestParameters.cacheParameterGroupName
```

公式APIの入力項目はEngineVersion、CacheParameterGroupNameです。両方とも任意指定です。CloudTrailでは上記のlowerCamelCaseのキーを確認対象とし、実イベントのJSONで表記と値を確認します。【R2】

両項目が必ず同じイベントに記録されるとは限りません。片方だけを指定する要求や、複数回の変更要求もあるため、対象RGの該当時間帯のイベントをまとめて確認します。

更新時とロールバック時に同じModifyReplicationGroupが呼ばれる可能性があります。イベント名だけでは区別せず、対象RG、時刻、要求値、エラーをCloudFormationのイベントと照合します。これは公式API仕様を今回の調査に当てはめた確認方法であり、今回の実呼び出しは未確認です。

## 2. Webコンソールでの具体的な確認手順

AWS公式のEvent historyの操作を、今回の対象に当てはめた手順です。【R3】

1. 作業対象のAWSアカウントでCloudTrailを開く。
2. リージョンを東京（ap-northeast-1）にする。
3. 左メニューの「イベント履歴／Event history」を開く。
4. 検索属性を「イベント名／Event name」にし、値をModifyReplicationGroupにする。既定の「読み取り専用／Read-only=false」が残っている場合は、検索属性を切り替えるか、そのフィルターを外す。
5. 時間範囲を、CloudFormationの更新開始からロールバック失敗までを含む範囲にする。最初は少し広く取り、該当イベントが見つかってから絞る。
6. 絶対期間を指定する場合は、JSTなどのローカル時間かUTCかを確認して入力する。
7. 一覧のModifyReplicationGroupをクリックする。
8. 詳細画面を下へスクロールし、「イベントレコード／Event record」に表示されるJSONを確認する。
9. requestParameters内のreplicationGroupIdを読み、対象のRedisであることを確認する。スタック名・論理IDではなく、ReplicationGroupの実際の識別子と照合する。
10. engineVersionとcacheParameterGroupNameを探して値を控える。requestParameters内の値であることを確認する。
11. eventTime、requestID、eventID、errorCode、errorMessageも控える。
12. 同じ時間帯の他のModifyReplicationGroupも開き、更新時・ロールバック時・手動操作時を分けて整理する。

イベント履歴で使えるのは「属性フィルター1つ＋時間範囲」です。イベント名とイベントソースを同時に属性条件として指定することはできません。【R3】

別の探し方として、検索属性を「イベントソース／Event source」、値をelasticache.amazonaws.comに変更できます。その場合、イベント名は一覧やJSONで確認します。

requestParameters.engineVersionやcacheParameterGroupNameは、イベント履歴の検索属性ではありません。イベント名・時間で絞ってJSONを読むか、「イベントのダウンロード／Download events」からJSONを保存して確認します。CSVの一覧だけで要求パラメータを確認したつもりにならないようにします。【R3】

## 3. JSONで控える項目と意味

| JSONの項目 | 確認内容 |
| --- | --- |
| eventSource | elasticache.amazonaws.comか |
| eventName | ModifyReplicationGroupなど、要求されたAPI名 |
| awsRegion | ap-northeast-1か |
| eventTime | 要求処理のUTC日時。Redisの更新完了日時とは別 |
| requestParameters.replicationGroupId | 対象Redisの実ID |
| requestParameters.engineVersion | その要求で送信されたバージョン。現在の実バージョンや変更前の値ではない |
| requestParameters.cacheParameterGroupName | その要求で送信されたPG名。Export名ではなく、解決後のグループ名を確認する |
| errorCode / errorMessage | サービスが返したエラー。存在する場合に確認する |
| requestID | 呼び出し先サービスが生成した要求ID |
| eventID | CloudTrailのイベントID。requestIDとは別 |
| userIdentity / userAgent | 呼び出し主体を調べる補助情報 |

JSONのeventTimeはUTCです。JSTへ換算する場合は9時間を加え、日付をまたぐ場合にも注意します。

フィールドの意味はAWS公式のCloudTrailレコード仕様に基づきます。各サービス入力の意味はElastiCacheのAPI仕様で確認します。【R2・R4】

JSONの形を示す説明用の例です。実際の取得ログではなく、両項目が必ず揃うという意味でもありません。

```json
{
  "eventSource": "elasticache.amazonaws.com",
  "eventName": "ModifyReplicationGroup",
  "awsRegion": "ap-northeast-1",
  "requestParameters": {
    "replicationGroupId": "<対象RGの実ID>",
    "engineVersion": "<実際に送信された値>",
    "cacheParameterGroupName": "<実際に送信されたPG名>"
  }
}
```

公式のElastiCache CloudTrailガイドには、API要求・応答のJSON例があります。ただし、その掲載例はModifyReplicationGroupで今回の2項目を同時に示した実例ではありません。今回のキーの有無と送信値は実ログで確認します。【R1】

## 4. 今回の事象との照合方法

利用者から共有された対応関係：

| PG名 | 共有されたFamily・位置付け |
| --- | --- |
| testf-awsel-8s50v98vj1ty | 旧カスタムPG、redis6.x |
| testfc-cache-rw8ceksexno | V2カスタムPG、redis7 |
| default.redis7.cluster.on | 手動アップグレード後に実環境で使用中と共有されたPG |

これらの現在の状態を、今回の調査で実環境へ接続して確認したものではありません。

### 更新時のPG互換性エラー

- CloudFormationでPG互換性エラーが出た時刻前後のModifyReplicationGroupを探す。
- 対象RGの要求にcacheParameterGroupName=testf-awsel-8s50v98vj1tyが記録されていれば、旧PG名を要求した証拠になる。
- engineVersionも同時に存在する場合は、そのままの値を控える。テンプレートの7.1と、サービスが返す7.1.0の表記を勝手に統一しない。
- 対象RG、errorMessage、時刻、可能ならElastiCacheのRequest IDを照合する。

### ロールバック時のダウングレードエラー

- CloudFormationがロールバックへ移った時刻以降の同じRGのイベントを探す。
- engineVersion=6.2.6が記録されていれば、その要求で旧バージョンを指定した証拠になる。
- エラー内容が、共有された「Cannot modify redis from 7.1.0 to redis version 6.2.6」と対応するか確認する。
- cacheParameterGroupNameが記録されている場合は、それも控える。更新時と同じPG名が必ず送られるとは断定しない。

ElastiCache公式は、ModifyReplicationGroupによるエンジンのダウングレードを認めていません。【R2】
ただし、今回実際にどの要求が送られたかは、この資料だけでは確定していません。

### CloudFormation起因かの照合

- 子スタックのAwsElastiCacheReplicationGroupのイベント時刻・エラーと照合する。
- userIdentity.arn、userIdentity.sessionContext.sessionIssuer、userIdentity.invokedBy、userAgentを、記録されている範囲で確認する。【R6】
- CloudFormationは、サービスロール指定時はそのロール、未指定時は利用者認証情報から生成する一時セッションを使う。そのため、呼び出し主体が常に同じ形式になるとは限らない。【R7】
- invokedByやuserAgentにcloudformation.amazonaws.comがあるかは参考になるが、必須条件として検索・判定しない。
- CloudTrailのrequestIDを照合するときは、ElastiCache呼び出しのRequest IDと比較する。親のExecuteChangeSetなど別APIのrequestIDと同じだとは仮定しない。【R4】

CloudFormation側のExecuteChangeSet／UpdateStackなどは、開始操作の確認用です。実際にElastiCacheへ渡したPG名・エンジン値の確認は、ElastiCache側の要求イベントを中心に行います。
CloudFormation公式のログ説明には、スタックの入力パラメータはキー名のみを記録し、値は記録しない旨のNoteがあります。【R5】

## 5. 調査対象イベント名の整理

| イベント名 | 主な用途 | engineVersion／cacheParameterGroupNameの確認 |
| --- | --- | --- |
| ModifyReplicationGroup | 既存RGの変更要求。本件で最初に探す | APIに両入力あり。送信・記録されていれば確認できる。【R2】 |
| ModifyCacheCluster | クラスター単位の変更要求 | APIに両入力あり。ただし今回CloudFormationがこのAPIを使ったとは未確認。【R8】 |
| CreateReplicationGroup | 新規作成・置換で、このAPIが呼ばれた場合 | APIに両入力あり。既存RGの更新イベントと混同しない。【R9】 |
| CreateCacheParameterGroup | V2などのPG作成 | cacheParameterGroupNameとcacheParameterGroupFamilyを確認する。EngineVersionの入力はない。【R10】 |
| ModifyCacheParameterGroup | PG内の設定値の変更 | PG名と変更パラメータを確認する。RGへのPG関連付け変更やEngineVersion変更のイベントではない。【R11】 |
| ExecuteChangeSet / UpdateStack | CloudFormation側の実行契機の確認 | eventSourceはcloudformation.amazonaws.com。ElastiCacheへの解決済み要求値と同一視しない。【R5】 |

CacheParameterGroupFamilyはModifyReplicationGroupの入力項目ではありません。
PG名がどのFamilyに属するかは、PGの設定、作成時のCreateCacheParameterGroup、保存済みの確認結果などと別途照合します。

## 6. 見つからない・値がない場合

- イベント履歴はリージョン単位・過去90日間の管理イベント。証跡を新規作成しなくても直近の履歴は確認できる。【R1・R3】
- 対象アカウント、東京リージョン、JST／UTC、時間範囲、フィルターを再確認する。
- 90日より前は、当時から保存されていた証跡のS3ログやCloudTrail Lakeなどの保存先を確認する。保存状況は現場で確認する。
- requestParametersは要求で送られた項目であり、毎回全設定を含むものではない。APIの任意項目が両方揃うことを前提にしない。【R2・R4】
- requestParametersにはサイズ超過による省略の仕様もある。項目がない場合、理由を未送信と断定せず、前後の要求も確認する。【R4】
- エラーは通常errorCode／errorMessageを確認するが、サービスによってresponseElementsに入る場合もある。【R4】
- エラー欄がないことだけでは、非同期のリソース更新やCloudFormation全体の成功を証明できない。【R2】
- ElastiCache公式ではDescribe*のCloudTrail responseElementsはnullと説明されている。DescribeReplicationGroupsのCloudTrailイベントから、実環境の現在値を取得できるとは考えない。【R1】
- ログが見つからないことだけで「CloudFormationはAPIを呼んでいない」と確定しない。記録の範囲と実適用版を確認する。

## 7. 現場AIへ渡す確認結果の書式

該当する要求が複数ある場合は、1イベントごとに記録します。値がない場合は「項目なし」、判断できない場合は「未確定」と記載します。

```text
区分：更新時／ロールバック時／手動操作時／未確定
対象AWSアカウント：
awsRegion：
eventTime（UTC）：
eventTime（JST換算）：
eventSource：
eventName：
requestParameters.replicationGroupId：
requestParameters.engineVersion：
requestParameters.cacheParameterGroupName：
errorCode：
errorMessage：
requestID：
eventID：
呼び出し主体（userIdentity等）：
対応するCloudFormationイベントの時刻・論理ID・エラー：
ログから確定できたこと：
まだ未確認のこと：
```

## 8. AWS公式根拠：URLとページ内の確認場所

### R1：ElastiCache APIのCloudTrail記録

- URL：https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/logging-using-cloudtrail.html
- 確認箇所：冒頭、Amazon ElastiCache information in CloudTrail、Understanding Amazon ElastiCache log file entries。
- ページ内検索：`eventSource`、`requestParameters`、`Describe*`。
- 根拠：ElastiCache APIの記録、証跡未設定時のイベント履歴、JSON例、Describe系応答の扱い。

### R2：ModifyReplicationGroupの要求パラメータ

- URL：https://docs.aws.amazon.com/AmazonElastiCache/latest/APIReference/API_ModifyReplicationGroup.html
- 確認箇所：Request Parameters → ReplicationGroupId、EngineVersion、CacheParameterGroupName、ApplyImmediately。
- 根拠：対象IDと変更要求値、2項目の任意指定、ダウングレード不可、非同期適用。

### R3：イベント履歴の画面操作・検索・90日制限

- URL：https://docs.aws.amazon.com/awscloudtrail/latest/userguide/view-cloudtrail-events-console.html
- 確認箇所：冒頭、To view Event history、Filtering CloudTrail events、Viewing details for an event、Downloading events、Customizing the display。
- ページ内検索：`single attribute`、`Event record`、`90 days`、`Event time display`。
- 根拠：1属性＋時間範囲、詳細JSON、ダウンロード、リージョン単位の90日履歴、表示時刻の切替。

### R4：CloudTrail JSONフィールドの意味・省略制限

- URL：https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference-record-contents.html
- 確認箇所：eventTime、eventName、requestParameters、errorCode、errorMessage、requestID、eventID。
- ページ内検索：上記のフィールド名。
- 根拠：UTC時刻、APIアクション名、実際の要求パラメータ、エラー、各ID。requestParametersのサイズ上限と省略規則。

### R5：CloudFormation側のCloudTrail記録

- URL：https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cfn-api-logging-cloudtrail.html
- 確認箇所：Understanding CloudFormation log file entries直下のNote、UpdateStackの例。
- ページ内検索：`Parameter values`、`UpdateStack`。
- 根拠：CloudFormation APIの記録と、スタック入力パラメータ値は記録しないという説明。

### R6：呼び出し主体の確認

- URL：https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference-user-identity.html
- 確認箇所：Fields → type、arn、invokedBy、sessionContext → sessionIssuer。
- 根拠：IAM主体、サービスからの呼び出し、一時認証情報の発行元の確認。

### R7：CloudFormationが使う認証情報

- URL：https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/using-iam-servicerole.html
- 確認箇所：冒頭のサービスロールと既定動作の説明。
- 根拠：サービスロール指定時と未指定時で、操作に使う認証情報の形が異なる。

### R8：ModifyCacheClusterの入力

- URL：https://docs.aws.amazon.com/AmazonElastiCache/latest/APIReference/API_ModifyCacheCluster.html
- 確認箇所：Request Parameters → CacheClusterId、EngineVersion、CacheParameterGroupName。
- 根拠：クラスター変更APIにも両項目がある。本件での使用有無は実ログ次第。

### R9：CreateReplicationGroupの入力

- URL：https://docs.aws.amazon.com/AmazonElastiCache/latest/APIReference/API_CreateReplicationGroup.html
- 確認箇所：Request Parameters → EngineVersion、CacheParameterGroupName。
- 根拠：作成APIにも両入力がある。

### R10：PG作成時のFamily確認

- URL：https://docs.aws.amazon.com/AmazonElastiCache/latest/APIReference/API_CreateCacheParameterGroup.html
- 確認箇所：Request Parameters → CacheParameterGroupFamily、CacheParameterGroupName。
- 根拠：PGの作成名とFamily。Redis本体のエンジン更新要求とは別。

### R11：PG内の設定変更

- URL：https://docs.aws.amazon.com/AmazonElastiCache/latest/APIReference/API_ModifyCacheParameterGroup.html
- 確認箇所：Request Parameters → CacheParameterGroupName、ParameterNameValues。
- 根拠：PG内のパラメータ値を変更するAPI。

## 9. 現場AIへの依頼

実イベントから、更新時・ロールバック時の対象RG、送信されたengineVersion／cacheParameterGroupName、エラーを抽出してください。
キーがなければ補完せず、未記録として扱ってください。手動アップグレード時のイベントと混同せず、CloudFormationの時系列と対応させてください。
ログで確認した事実と、テンプレート構造からの推論を分けて回答してください。
